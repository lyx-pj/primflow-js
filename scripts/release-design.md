The release script owns local files, Git commits, and publication side effects. Changesets owns version planning and changelogs. Pages builds a selected snapshot. No new domain classes, dependencies, or public APIs are needed.

## Normal flow

1. Require `main` and a clean worktree. Validate remote configuration and read remote `main` and release branch state. Remote `main` must be an ancestor of local `main`; reject divergence without automatic merging or resetting. Stop if remote state cannot be read.
2. Preserve `pnpm lint`, `pnpm test`, and `pnpm typecheck`. Record versions before running `pnpm changeset version`, validate the unified result, and synchronize the root version.
3. If versions are unchanged and retry conditions below do not apply, report no pending release and exit without committing, publishing, or pushing. Stop for inspection if other changes occurred without a version increment.
4. Derive the branch name from the new version, check local and remote branch conflicts, then run `pnpm build`. Do not commit a failed build. Stage only files generated by this versioning flow and check staged content again to exclude unrelated files.
5. Create the `chore(release): vX.Y.Z` commit and local version branch, then run the existing recursive npm publication command.
6. After npm succeeds, push atomically. Constrain new remote release branches to an expected absent state to prevent races; retain fast-forward requirements for `main`. Do not fall back to separate pushes or forcibly overwrite refs.
7. The first remote update of the release branch triggers Pages, building that commit rather than the latest `main`. Preserve existing build and deployment steps.

## Failure, repetition, and cancellation

| Scenario                                                                                                           | Handling                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing changes, non-`main` branch, inconsistent versions, branch conflicts, or remote query failures             | Stop before npm publication with a reason. Never automatically stash, switch, delete branches, or reset files.                                                                                                                    |
| Checks, versioning, build, or commit failure                                                                       | Stop subsequent steps and preserve state. If version files changed, ask the operator to inspect and restore generated files before retrying; do not clean up existing changes automatically.                                      |
| Partial npm failure or interruption                                                                                | Do not push; preserve the local release commit and branch. On a clean retry, recognize that commit and reuse its version without another bump or commit. Repeat checks and builds, then recursively publish unpublished versions. |
| npm success followed by Git push failure                                                                           | Retry the same local snapshot without changing package versions. Stop for manual resolution if remote `main` diverged; never automatically rebase a published snapshot.                                                           |
| No changeset, with HEAD subject, root and library versions, and local release branch identifying the same snapshot | Treat as a retry. Continue only if the remote release branch is absent or points to that commit. Otherwise do not guess recovery state.                                                                                           |
| Repeating an already pushed snapshot                                                                               | Do not create commits or move release branches. Pushing unchanged refs does not create another deployment. Retry failed Pages runs or manually select that release branch.                                                        |
| Pages failure                                                                                                      | Do not roll back npm. Retry Pages independently without withdrawing published versions.                                                                                                                                           |

Atomic Git pushes cover Git refs only; npm and Git cannot form one transaction. Retaining the release snapshot enables reviewable recovery. Recursive publication retains pnpm handling of published versions without adding `--force`.

Validate that a single-package changeset upgrades all four libraries in a temporary workspace without changing actual worktree versions. Validate commitlint, workflow events, and snapshot checks. Perform no real commits, remote pushes, npm publication, or live deployment.

## External conditions and tradeoffs

- Publishers need permission to push `main`. If policy requires a PR, stop without bypassing it.
- The Git remote must support atomic pushes; otherwise stop and preserve retry state. [Git documentation](https://git-scm.com/docs/git-push) defines the all-or-nothing behavior.
- The `github-pages` environment may restrict deployment branches. Before the first release, verify that it permits `release/v*`; do not change live environment policies as part of this work. [GitHub documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) explains environment restrictions.
- Releases share one Pages site and retain existing concurrency behavior. Preserve versioned Git snapshots without adding separately hosted sites per version.

- Specification r2 / design d1. Baseline: the original release script with 11 passing release tests.
- Initial failing regression: `pnpm test:release` produced three expected failures, showing the old commit subject and publication/pushing without version changes.

With `privatePackages: false`, its manifest stays unchanged. Default peer dependency rules can increase the bump level; a real fixture upgrading all four libraries to `1.0.0` verifies that behavior, documented in both READMEs.
- Final `pnpm test:release`: 37/37 passed, covering REL-01 through REL-07: no changes, unified bumps and root synchronization, inconsistent versions, unrelated staged files, build modifications, branch collisions, failures and retries, and Pages snapshot matching and event configuration.
- The commit subject passed existing `pnpm exec commitlint`. All four relevant TypeScript files passed standalone strict type checking and existing oxlint configuration checks.
- Implementation adds `scripts/release-version.ts` for shared version/snapshot validation and `scripts/validate-release.ts` as the Pages validation entry point, verified through existing release test infrastructure.
- Tokens, fees, and end-to-end duration were not collected; no cost improvement is claimed. No real Git commits, pushes, npm publication, or Pages deployment occurred. Library code and dependency boundaries were unchanged, so no full repository build was run.
- Live validation remains for the first actual release: remote atomic pushes, main branch policies, and the `github-pages` environment’s release branch rules.
