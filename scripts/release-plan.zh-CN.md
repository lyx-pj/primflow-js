# 发布与 Pages 触发调整规格

[English](release-plan.md) | 简体中文

修订：r2；状态：已确认。设计见 [发布设计](release-design.zh-CN.md)。
需求来源：用户希望发布时建立版本分支，以明确的 release 提交记录版本更新，仅在发布更新时自动部署 Pages。

## 当前行为与目标

`scripts/release.ts` 运行检查、Changesets 版本更新和构建，在当前分支提交 `chore: bump versions [skip ci]`，发布 npm 包后推送。Pages workflow 监听所有 `main` 推送，也支持手动运行。

目标是让在线示例对应明确的发布快照，并避免日常开发提交触发部署。四个库包统一版本，继续由 Changesets 管理版本递增和内部依赖，不新增依赖，不执行实际发布或推送。

## 需求与验收

| 标识   | 需求与验收                                                                                                                                                                                                             |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REL-01 | 成功的版本发布产生 `release/vX.Y.Z` 分支和 `chore(release): vX.Y.Z` 提交，提交不含 `[skip ci]`，且通过仓库现有 commitlint 配置。                                                                                       |
| REL-02 | 日常 `main` 推送不自动部署 Pages；发布分支的发布提交触发部署，构建该发布快照。保留手动触发。                                                                                                                           |
| REL-03 | 保留工作区清洁检查、lint、测试、类型检查、构建及 npm 发布步骤；前置步骤失败时不继续发布或推送。                                                                                                                        |
| REL-04 | 无版本变化时不生成空发布提交或重复部署；发布中途失败后可重试，具体恢复规则在设计阶段确认。                                                                                                                             |
| REL-05 | 在执行外部发布前检查分支名、版本标识及同名分支冲突；不覆盖既有发布分支。                                                                                                                                               |
| REL-06 | 更新中英文使用说明，并用模拟命令测试发布流程，不执行真实提交、推送或 npm 发布。                                                                                                                                        |
| REL-07 | 四个库包使用 Changesets `fixed` 分组，共同升级、共同发布；根据本次 changesets 自动计算统一版本，无需额外版本参数或交互。分支名和提交信息自动读取生成的版本。版本不一致时阻止发布，不使用根版本覆盖 Changesets 的结果。 |

## 已确认规则

1. 版本更新提交保留在 `main`，发布分支指向同一提交，使后续 Changesets 基于最新版本继续工作。
2. 用户已明确要求统一版本、无需额外选择版本号。使用 `fixed` 分组，让四个库包按 Changesets 计算结果统一升级；根私有包版本同步为该结果，示例私有包不参与 npm 发布版本管理。根版本同步方向与旧 `sync-versions.ts` 相反，不将其加入发布流程。
3. 提交格式采用 `chore(release): v0.0.7`，已通过仓库 commitlint；分支为 `release/v0.0.7`，二者均自动取自统一版本。发布命令仍为 `pnpm release`，不增加参数。
4. 保留 Pages 手动触发，便于重试部署；自动触发仅接受发布更新。

## 评测计划

基线来自当前脚本、现有发布测试及 Pages workflow。此前 commitlint 验证通过；规格确认后运行 `pnpm test:release`，现有 11 项测试全部通过。这些测试描述原有行为，尚不验证新设计。

实现时先运行最小失败回归，再运行 `pnpm test:release`，覆盖普通发布、单包 changeset 引起全组统一升级、无变化、版本一致性校验、分支冲突、检查失败、发布失败、推送失败和重试；核对 Pages 事件及 checkout 的来源。模拟验证不等同于线上部署验证，真实 GitHub Pages 结果需首次正式发布时确认。发布逻辑修改不涉及库产物，除非实际改动扩展到包边界，否则不额外执行全仓库构建。
