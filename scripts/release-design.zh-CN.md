## 规则与职责

| 规则 | 设计                                                                                                                                                                                                                                    | 验收                   |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| D-01 | `.changeset/config.json` 将 model、engine、canvas、react 四个库列入同一 `fixed` 分组；不使用 `linked`。用 `privatePackages: false` 排除私有示例，根版本由脚本同步。版本递增仍由 Changesets 决定，保留 peerDependencies 的默认升级规则。 | REL-07                 |
| D-02 | `scripts/release.ts` 读取 Changesets 生成的四个版本，校验一致且符合版本格式，再同步根私有包版本。根版本不是升版来源；不调用旧 `sync-versions.ts`。                                                                                      | REL-01、REL-07         |
| D-03 | 发布提交为 `chore(release): vX.Y.Z`，保留在 `main`；本地 `release/vX.Y.Z` 指向同一提交，不切换分支。发布分支视为不可变快照，不追加开发提交。                                                                                            | REL-01、REL-05         |
| D-04 | npm 发布全部成功后，原子推送 `main`、发布分支和现有流程产生的关联标签；不新增独立打标签流程。远端发布分支只允许首次创建或已指向同一提交，不能移动到另一提交。                                                                           | REL-02、REL-04、REL-05 |
| D-05 | Pages 自动监听 `release/v*` 推送；部署前校验分支名、统一版本及提交标题相互匹配，再构建事件所指的提交。普通 `main` 推送不会触发该 workflow。手动运行也须选择匹配的发布分支。                                                             | REL-02                 |

发布脚本负责本地文件、Git 提交和发布副作用；Changesets 负责版本规划与 changelog；Pages 负责构建指定快照。无需新增领域类、依赖或公共 API。

## 正常流程

1. 要求当前为 `main` 且工作区清洁，校验远端配置并读取远端 `main` 和发布分支状态；远端 `main` 必须为本地 `main` 的祖先，禁止分叉发布，不自动合并或重置。远端无法读取即停止。
2. 保留 `pnpm lint`、`pnpm test`、`pnpm typecheck`。记录升版前版本，运行 `pnpm changeset version`，校验四库统一结果并同步根版本。
3. 没有版本变化且不符合下述重试条件时，提示没有待发布版本并退出，不提交、不发布、不推送。版本没有升级却产生其他变更时停止并提示检查。
4. 根据新版本生成分支名，校验本地、远端同名分支无冲突；运行 `pnpm build`。构建失败不提交。只暂存本次版本流程生成的文件，提交前再次检查待提交内容，避免把无关文件带入发布提交。
5. 创建 `chore(release): vX.Y.Z` 提交和指向该提交的本地版本分支，再运行既有递归 npm 发布命令。
6. npm 发布成功后进行原子推送。对新建远端发布分支使用预期不存在的约束，避免检查与推送之间的竞争；对 `main` 保持快进要求。原子推送失败不降级为分开推送，不自动强制覆盖。
7. 发布分支的首次远端更新触发 Pages；部署构建该提交，而非执行时最新的 `main`。检查和构建方式沿用现有 workflow。

## 失败、重复与取消

| 场景                                                                  | 处理                                                                                                                                               |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 已有未提交修改、非 `main`、版本不一致、分支冲突或远端查询失败         | 在 npm 发布之前停止并给出原因；不自动 stash、切换、删除分支或重置文件。                                                                            |
| 检查、升版、构建、提交失败                                            | 后续步骤停止；保留现场。若版本文件已修改，提示用户检查并恢复本次生成文件后重试，不自动清理已有改动。                                               |
| npm 部分失败或用户中断                                                | 不推送；保留本地发布提交和版本分支。清洁工作区下重跑 `pnpm release` 识别该提交，复用其版本，不再升版或提交，重新检查、构建并递归发布未发布的版本。 |
| npm 成功、Git 推送失败                                                | 同样复用本地发布快照重试；不改包版本。若远端 `main` 已分叉，停止并说明需人工解决；不自动 rebase 已发布快照。                                       |
| 无 changeset，HEAD 标题、根及四库版本、本地发布分支均对应同一发布快照 | 视为可重试发布；同名远端分支缺失或指向同一提交才允许继续。未满足这些条件时不猜测恢复状态。                                                         |
| 同一快照已推送，再次运行发布                                          | 不生成新提交或移动发布分支；相同 ref 的重复推送不产生新部署。Pages 失败时从原 workflow 重跑或手动选择该发布分支。                                  |
| Pages 失败                                                            | npm 发布不会回滚；独立重试 Pages，不撤销已发布版本。                                                                                               |

Git 原子推送只覆盖 Git refs，不能把 npm 和 Git 合并成一个事务。保留发布快照用于恢复，比失败时自动回滚更容易审查。递归发布沿用 pnpm 对已发布版本的处理，不加入 `--force`。

## 改动位置与验证

- `.changeset/config.json`：统一版本分组。
- `scripts/release.ts`、`scripts/release.test.ts`：发布流程及模拟副作用的失败回归。
- `.github/workflows/pages.yml`：事件筛选、发布快照校验、按事件提交 checkout；保留构建与部署步骤。
- 根中英文 README：发布方法、统一版本和 Pages 行为说明。旧版本同步命令不再推荐用于发布。

先写并运行失败测试，再实现并运行 `pnpm test:release`。保留当前 11 项用例的有效检查，按新行为调整无变化与推送断言，并覆盖 REL-01 至 REL-07。使用临时工作区验证单包 changeset 引起四库统一升版，不修改真实工作区版本。验证 commitlint、workflow 触发条件和快照校验；不执行真实提交、远端推送、npm 发布或线上部署。

基线：旧发布测试 11/11 通过，目标行为尚未实现。依赖方向和库 API 不变，无需为此修改库源码或扩大到全仓库构建。

## 外部条件与取舍

- 发布者需要正常推送 `main` 的权限；若分支策略要求 PR，脚本停止，不绕过策略。
- Git 远端需要支持原子推送，否则停止并保留可重试现场。[Git 文档](https://git-scm.com/docs/git-push)定义其全有或全无语义。
- `github-pages` 环境可能限制可部署分支；首次发布前需核对是否允许 `release/v*`，本次不修改线上环境策略。[GitHub 文档](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)说明环境保护可能限制部署来源。
- 多次发布共享一个 Pages 站点，沿用现有 concurrency，保留每个版本的 Git 快照，不提供按版本独立托管。

- 规格 r2 / 设计 d1；基线为原发布脚本及 11 项通过的发布测试。
- 首次失败回归：`pnpm test:release` 出现 3 项预期失败，证明旧流程仍使用旧提交标题，且无版本变化仍发布、推送。

- 最终 `pnpm test:release`：37/37 通过，覆盖 REL-01 至 REL-07，包括无变化、统一升版及根版本同步、版本不一致、暂存区夹带文件、构建额外改动、分支冲突、各阶段失败与重试，以及 Pages 快照匹配与事件配置。
- 提交标题通过现有 `pnpm exec commitlint`；四个相关 TypeScript 文件通过独立严格类型检查和现有 oxlint 配置检查。
- 新增 `scripts/release-version.ts` 共享版本及快照校验，`scripts/validate-release.ts` 作为 Pages 校验入口；使用原发布测试基础设施验证。
- 未采集 token、费用及端到端耗时，不声称成本改善。未执行真实 Git 提交、推送、npm 发布或 Pages 部署；未改动库代码或依赖边界，因此未运行全仓库构建。
